# 社区设备适配 Wiki

这份指南帮助你为外设盒（Peripheral Desk）新增设备驱动，并通过 Pull Request（PR）贡献。设备插件独立打包，用户只安装自己需要的设备；新增型号通常不需要把设备代码塞进主程序。

## 先找到现有工作

提交代码前，先查看：

- [设备目录](DEVICE-CATALOG.md)：已有设备、型号、连接方式和支持范围。
- [兼容表](COMPATIBILITY.md)：每个包当前的功能及验证状态。
- [Vigil Watt 迁移清单](VIGIL-WATT-MIGRATION.md)：电量实现的上游型号范围和来源。
- [上游实现与证据复用规则](UPSTREAM-REUSE.md)：如何使用已验证协议、记录证据和遵守许可证。
- [适配任务列表](ADAPTATION-ROADMAP.md)：当前待办及验收边界。
- [设备插件模板](../templates/device/README.md)：ABI 1 插件的最小结构。

也可以先通过 [“申请适配新设备” Issue 表单](../.github/ISSUE_TEMPLATE/device.yml) 提交资料。PR 的检查项目见 [Pull Request 模板](../.github/PULL_REQUEST_TEMPLATE.md)。

## 第一步：精确描述设备

记录你实际要适配的**品牌、完整型号、代际/硬件版本、固件版本和连接方式**。连接方式应具体到 USB、有线数据模式、2.4 GHz 接收器（注明普通或高回报率接收器）、蓝牙或底座。不同连接方式可能是不同协议，需分别记录。

若资料可得，再记录 VID/PID、HID usage page/usage、输入/输出/feature 报告长度、产品名和操作系统版本。VID/PID 是设备身份线索，不是协议兼容证明；同 VID/PID、同品牌或外观相似都不能自动扩展支持范围。运行时识别条件应尽量精确，避免把命令发给另一台设备。

不要在公开 Issue 或 PR 上传序列号、用户名、机器名、本机路径、完整原始 HID 报文或含个人信息的日志。需要分享协议证据时，只保留解释字段所需的最小片段，并去除身份信息。

## 第二步：找可复用的协议实现

先检查本仓库中相近的插件和协议模块，再查找厂商公开资料、官方驱动可读源码、协议文档及维护中的开源实现。优先固定到不可变的提交 SHA，并链接到具体源码、设备文档或验证记录；“仓库支持这个品牌”不足以作为型号依据。

对每项功能分别记录证据：例如电量读取、DPI 设置、改键和灯效可能来自不同实现，也可能只适用于不同固件或连接路径。上游真实设备报告只覆盖报告中明确写出的型号、固件、接收器和操作；它不等于本项目已经实机验证。

复用代码前检查被复制文件实际适用的许可证，而不只看仓库首页。保留版权和许可证文本，在插件的来源说明中写清上游仓库、提交、文件、修改情况及适用型号。只参考协议事实并自行实现时也要记录来源。没有兼容再发布许可的厂商 DLL、SDK、固件和私有数据不要放进公开插件包。

## 第三步：创建独立插件

从 [`templates/device`](../templates/device/README.md) 开始。常见改动包括：

1. 在 `drivers/<device-id>/` 创建独立 Cargo 插件，crate 名为 `<device-id>-driver`，库类型为 `cdylib`。
2. 加入根 `Cargo.toml` workspace，并在 `Cargo.lock` 中更新依赖锁定信息。
3. 实现 ABI 1 约定的三项导出和 JSON 请求/响应；参照 [ABI 文档](ABI.md)。所有返回缓冲区由创建它的 DLL 释放。未知操作应返回明确错误。
4. 在 `drivers-preview.json`（通常先以预览版贡献）加入完整设备条目：精确 `matches`、设备图片、主程序兼容范围、能力、用户可见变更和验证来源。设备 `key` 必须与包 `id` 一致，DLL 名为 `driver.dll`。
5. 添加设备图片，并在兼容表和来源文档中记录型号、连接路径、功能边界和证据。

共享协议可以放在公共 crate 中，但每个具体型号仍须有独立 catalog 条目和明确的匹配范围。只有确实共用协议、且上游证据覆盖的型号才能复用同一个底层实现。

## 第四步：准确声明能力与验证状态

界面只应展示插件真实实现的能力。不要为了填满页面声明 DPI、回报率、改键、宏、灯光或音效；电量插件只声明电量。主动发送查询帧的协议要说明其主动性质，并沿用插件按需安装和设备隔离策略。

解析失败、字段缺失、回复不匹配、设备离线或缓存过期时，应返回错误/未知或明确标记缓存。不能将这些情况转换成 `100%`、默认设置或看似成功的状态。写设置前只在协议支持的情况下保存必要原值；写入失败时按上游事务语义尝试恢复，并报告恢复结果。保留无法识别的数据字段，避免清零或覆盖。

兼容记录应区分：

- `upstream-hardware-verified-project-untested`：精确范围有上游实物验证依据；本项目尚未做对应实机验证。
- `public-implementation-untested`：有公开协议实现，但没有目标范围的可靠实物报告。
- 本项目实机验证：只在本项目确实连接目标设备并验证对应功能后记录，写明连接方式和固件；不要用上游结果冒充。
- 仅能识别/未支持：能识别设备但没有可用功能时如实说明，不能伪装成完整插件。

目录状态枚举以 `scripts/check-source.py` 和现有 catalog 为准。证据未覆盖某条连接方式或某项写入时，将其排除或保持关闭，并在兼容表说明原因。

## 第五步：做必要的软件检查

Windows x64 开发环境需要 Rust stable（含 `rustfmt`、`clippy`）、Python 3.11+ 和本仓库依赖。首次构建可能需要网络下载 Cargo 依赖。使用独立任务目录存放 Cargo 构建输出，避免污染源码：

```powershell
$env:CARGO_TARGET_DIR = "D:\CODEX\Tasks\work\driver-target"
python scripts/check-source.py
cargo fmt --all -- --check
cargo clippy --locked -p <device-id>-driver --all-targets -- -D warnings -A clippy::field-reassign-with-default
cargo test --locked -p <device-id>-driver --lib
python scripts/build.py --metadata drivers-preview.json --package <device-id> --target x86_64-pc-windows-msvc
```

把 `<device-id>` 换成 catalog 中的设备 id。针对纯文档修改无需运行 Rust 构建。协议解析若有独立共享 crate，应对该 crate 做对应的格式、lint 和解析检查。不要为与本次改动无关的设备重复跑整套测试；上游精确型号和连接方式的验证材料可以作为协议证据保留。

本地构建的插件包不等于可由商店安装的正式包：主程序只接受维护者发布并签名的目录及其校验匹配的插件。PR 的 CI 产物用于审阅，不会被自动加入正式驱动商店。离线安装也需要同一可信发布的目录签名文件。

## 第六步：提交 PR

提交前确认：

- 型号、代际、固件和每种连接路径都写清楚；匹配规则不会误选别的设备。
- 功能与证据逐项对应，实测范围和未知项如实记录。
- 上游代码来源、固定提交、许可证和版权声明齐全；没有未经许可的厂商二进制或私密数据。
- 更新了插件 metadata、兼容表、来源说明和用户可见 changelog。
- 运行了与本次改动相关的检查，说明命令及结果；未实测的硬件操作明确标为未验证。
- 只包含本设备及其确需的共享协议改动，不覆盖其他贡献者的本地工作。

在 PR 中用普通用户能理解的话写清楚：支持哪个型号和连接方式、用户能做什么、需要什么限制、如何恢复，以及还没有验证什么。维护者审核后会决定是否合并、签名并发布到 stable 或 preview 驱动目录。

## 给编程 Agent 的适配提示词

复制下面整段，将方括号内的信息替换为你的设备资料。没有的信息写“未知”，不要让 Agent 猜测：

```text
你要为 Peripheral Desk / 外设盒的公开驱动仓库贡献一款设备插件，并准备一个可审阅的 Pull Request 改动。请直接在我提供的仓库中检查并实现，不要重建项目，不要覆盖或回退无关的本地修改。

目标设备：
- 品牌与完整型号：[填写]
- 代际/硬件版本：[填写或未知]
- 固件与官方软件版本：[填写或未知]
- 目标连接方式：[USB/有线/普通 2.4 GHz 接收器/高回报率接收器/蓝牙/底座，逐项填写]
- 已知 VID/PID、HID usage、报告长度：[填写；未知就写未知]
- 我希望支持的功能：[电量/充电状态/DPI/回报率/休眠/改键/宏/灯光/音效，逐项列出]
- 我能提供的公开资料或上游链接：[填写；没有就写无]
- 我实际验证过的设备、连接和功能：[填写；未实测就写未实测]

开始前：
1. 阅读仓库 AGENTS.md（如果存在）、CONTRIBUTING.md、docs/COMMUNITY-ADAPTATION-WIKI.md、docs/UPSTREAM-REUSE.md、docs/ABI.md、docs/COMPATIBILITY.md 和设备模板。
2. 检查 git status、现有设备目录、兼容记录、catalog 和相关协议实现，先找是否已有同型号或共用协议工作。保留所有无关改动，不要清理、暂存或改写我的其他文件。
3. 搜索并核对精确型号、固件和连接方式对应的官方或开源实现。优先采用可固定到提交 SHA 的成熟上游代码和明确的用户实物验证记录。核实实际拟复用文件的许可证；保留版权/许可证，记录来源版本、文件和改动。不要因品牌相同、VID/PID 相同或外观相似推断兼容。不得把未授权的厂商 DLL、SDK、固件或用户私密数据放入公开包。

实现要求：
1. 用现有 ABI 1 设备插件模板创建独立插件；按现有 workspace、catalog、签名、按需下载和离线包规则集成，不要把所有设备实现加入主程序。
2. 只有证据覆盖的型号、连接路径和功能才可启用。把设备身份匹配写准确；主动查询和被动监听要区分。未知值、过期缓存、未匹配回复或解析错误不得伪装为成功、100% 电量或默认设置。
3. 若实现写入功能，沿用上游事务语义；保存可恢复的原值，按已知协议读回验证，失败时尝试恢复并报告结果。保留未知配置字段。不要凭空添加空按钮、能力声明或不工作的控制项。
4. 更新预览 catalog、设备兼容记录、上游来源/许可证说明、插件说明和普通用户可读的 changelog。验证状态分别写清“上游硬件验证”“本项目实机验证”“仅公开实现未实测”或“仅能识别”。不得把上游实测说成本项目实测。
5. 尽可能少做重复测试。运行本次改动所需的 source/metadata、格式、目标插件构建、接口和解析检查；不跑无关整套设备测试，不要求我拥有未提供的实物。不要向硬件发送未经授权或无资料依据的命令。
6. 不要自行提交、推送、发布或创建 GitHub Release，除非我在当前任务明确要求；不要触碰签名私钥。

完成后给我：改动文件清单；每项功能的证据、精确适用型号/连接方式和验证状态；运行过的检查及结果；仍未支持或未知的内容；建议 PR 标题和简短说明。若证据不足以安全实现某项功能，保留它为未支持并说明缺少的具体依据，不要用猜测填充。
```
